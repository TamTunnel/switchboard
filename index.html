Switchboard

A local task bus for coding agents. Think of it like email for agents: any agent with shell access can send a task to any other agent with one command, and the result comes back to the sender's inbox. No central server, no account, no cloud — everything lives on your machine, in plain files you can read.

Source on GitHub · Live demo walkthrough · Explainer video · Apache-2.0

The problem

You run more than one coding agent — Claude Code in one terminal, Codex in another, OpenCode somewhere else. Sooner or later you want one of them to hand work to another: "you've explored the codebase, now have the other agent implement the fix," or "review this diff before I merge."

Today that handoff is you. You copy context out of one terminal, paste it into another, re-explain the task, and hope nothing got lost. The agents can't talk to each other, so you become the bus — a slow, lossy, human-shaped one.

The solution, in plain terms

# From any agent's terminal: hand a task to another agent
sb send --to codex --title "Implement rate limiting" \
  --instructions "Add per-key rate limiting to the API. See NOTES.md for the design."

# Later, check what came back
sb inbox

A daemon owns the queue. Tasks are sb/1 envelopes — a title, markdown instructions, done-criteria, constraints, context refs, and provenance (who sent it) — stored as plain JSON in a maildir store under ~/.switchboard/:

pending/ → claimed/ → done/   ·   failures → dead/

The daemon serves a local API on a Unix socket only (0600, no network listener in v1). Adapters are separate processes speaking versioned NDJSON over stdio; the built-ins cover echo, claude, codex, and opencode, and anyone can implement the adapter protocol.

Demo walkthrough — real output, echo adapter

This walkthrough was run against the real Switchboard binary (built from the repo) with the built-in echo reference adapter. IDs, timestamps, and outputs below are verbatim from that run. The real-agent adapters are covered in Honest limits below.

Shape 1: delegate — A → B, result returns to A

$ sb send --to echo --title "Hello from the bus" \
    --instructions "Say hello back, and confirm which agent you are."

$ sb inbox

$ sb logs 01M5TSA2XAWVWMQ7AFT4JB6ATQ

The result comes back as its own envelope (kind: "result", reply_to pointing at the task) in the sender's inbox — the "email, not Slack" play.

End of run — the maildir tells the story

$ for d in pending claimed done dead; do echo "$d: $(ls ~/$d | wc -l) files"; done
$ sb dead
pending: 0 files
claimed: 0 files
done: 7 files
dead: 0 files
(no dead letters)

Three tasks sent, three results in the inbox, nothing stranded, nothing silently dropped. When something does fail, it goes to dead/ with the error attached — and the origin agent gets a failure notification in its inbox.

All three handoff shapes

ShapeFlowCommand
DelegateA → B, result returns to Asb send --to codex --title "Fix the flaky test" …
PipelineA → B → C, final result returns to Asb send --to claude --shape pipeline --next codex --next opencode …
ReviewB reviews A's diff, comments return to Asb send --to claude --shape review --diff-file changes.diff …

Routing is explicit: --to takes an agent name, or a capability tag like --to cap:review (first agent declaring that capability wins). No model picks the agent for you.

Honest limits

What this demo does — and does not — prove

  • Demo uses the echo reference adapter. The claude, codex, and opencode adapters are implemented against their CLIs' documented flags and unit-tested against scripted stand-ins emitting the documented formats. None has been live-tested against the real CLI in this project's build environment. Known Codex failure mode, named plainly: an approval prompt can hang a non-interactive codex exec until the daemon timeout fires, then one retry, then dead-letter.
  • Task-level handoff only. v1 translates a structured task spec + file refs + transcript excerpt into the target agent's prompt. Full-fidelity portability between agent session formats is post-v1 and is not claimed anywhere.
  • Local only. Same machine, same workspace. Network/remote agents are explicitly out of scope for v1. The Unix socket is the only identity boundary: From is sender-asserted, not daemon-verified — provenance is a display string, not a trust signal, and receiving agents are told to treat handoff instructions as data from an untrusted peer.
  • Setsid escape. An adapter that escapes its process group (e.g. via setsid/daemonization) cannot be killed on daemon restart or shutdown; cgroup supervision that would close that hole is out of v1 scope.
  • Size limits. 1MB per envelope, 128KB rendered prompt, pipelines capped at 64 stages, transcript excerpts at ~8000 characters. Oversized sends are rejected immediately with a clear error.

Try it

# Build (Go 1.23+, static binaries, no runtime to install)
git clone https://github.com/TamTunnel/switchboard
cd switchboard
CGO_ENABLED=0 go build -o /usr/local/bin/switchboard ./cmd/switchboard
CGO_ENABLED=0 go build -o /usr/local/bin/sb ./cmd/sb
CGO_ENABLED=0 go build -o /usr/local/bin/sb-adapter ./cmd/sb-adapter

# Terminal 1: start the daemon (it owns the queue)
switchboard daemon

# Terminal 2: send a task, then check results
sb send --to echo --title "Hello" --instructions "Say hello back."
sb inbox          # results land here
sb status <id>    # full envelope as JSON
sb logs <id>      # adapter run log
sb dead           # dead-lettered envelopes and why they failed

Keep it running with the systemd unit or launchd plist in deploy/. See the README for architecture, the adapter protocol, and the full FAQ.
